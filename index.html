Compass · Retailer Assistant · Path §3

Pill registry and resolver

Companion to Luan’s RA Pill Identity Infra (Path §3). Replaces the kind → IntentType(kind) stub. Routing: RA Intent Routing Infra.

v22 · plan · open items are marked, not decided

TL;DR
  • A pill is a suggested question the retailer can tap instead of typing. Every pill carries one string, its pill key, and that key is the only thing a tap sends back.
  • One Python registry in RA lists every pill kind (a frozen name like sold_on_amazon) with the intent it opens and the question it asks.
  • Every tap goes through one function, resolve(pill_key): a bare kind reads the registry; a kind:uuid reads a per-pill record written when the pill was offered; anything else is treated as typed text.
  • Follow-up pills are written by the model but may only use registered kinds; the server mints the uuid and stores the exact question, so the tap replays what was offered.
  • Per-pill records move from a per-turn field in session state to a BE table with a TTL. No data migration: nothing is copied; the new table is simply written from the first deploy onward.

Why a registry. Today a tap is handled three ways (initial pills run as typed text with a key-picked prompt, compare is an intent the frontend asserts, generated follow-ups look up a one-turn map). One registry gives: the same behaviour for a kind wherever it is offered; latency, because a pill can declare work to run before the model; control over which follow-ups are offered, hidden or pinned; and a stable unit (the kind) to measure tap rate and run pill tests on.

02 Terms

Names used in the rest of this document, in the order they build on each other. Vocabulary follows the hub page; nothing here is new jargon. “Pill” is the only noun for the thing a retailer taps; “button” is what the frontend renders for it.

Identity

Pill
A suggested question shown as a button. The retailer taps it instead of typing. Two kinds of pill exist in the product: initial pills on the product page strip, and follow-up pills under an assistant reply.
Label
The text on the button (“Is this on Amazon?”). Shown to the retailer; never used to decide what happens on tap.
Prompt
The question the assistant actually runs when the pill is tapped (“Is this sold on Amazon? Compare the price if you find it.”). It becomes the next user message. Label and prompt differ because the button must be short and the question must be exact — a follow-up that says “Cheaper options” needs to ask for “under $18.40”, not “cheaper”.
Kind
A frozen lower_snake name for one behaviour: sold_on_amazon, compare_similar_products, mlt_add. A kind fixes the intent and, for initial and preset pills, the prompt. Many kinds can point at one intent, or at none. Two pills of the same kind always open the same intent; whether they share a prompt depends on who writes the ask (below). Locale differences (amazon.com vs amazon.co.uk) belong in the kind’s preload, not in new kinds.
Pill key (pill_key)
The one string a pill carries and a tap echoes back. Generally kind:uuid. A bare kind is used for initial pills and for preset follow-ups. ask:uuid and ask_<intent>:uuid are the generic kinds for model-written pills with no named kind (no intent / that intent). A leading : with no kind is rejected. The frontend treats the key as opaque; the warehouse derives pill_kind from the part before :.
Intent
A job the assistant knows how to do (compare, more like this, product research). An intent owns the playbook that answers; a pill only carries its ask.

Registry

Registry (REGISTRIES.pills)
A Python registry in the RA app, like REGISTRIES.tools. Engineers add rows in code under core/pills/; follow-up rows are registered from the intent folder with REGISTRIES.add_follow_up(...). It is not a database table. A duplicate kind fails at import.
PillSpec
One registry row: kind, intent, optional fixed prompt, optional fixed English label, eligibility for initial pills, preload. Given a bare kind, this is all a tap needs.
FollowUpPill
A PillSpec plus what the model needs to offer it: docs (when to use it), an optional per-pill check, and an optional pydantic model for the fields the model fills.
Manifest
A checked-in list of the kinds the DAG may serve as initial pills (kind → intent, eligibility, fixed label if any). A test keeps it equal to the registry; an Airflow test fails if the DAG serves a key that is not in it. It is the contract between two repos that do not import each other.

Per tap

Tap
The retailer presses a pill. The frontend sends a PillClickAction carrying the pill key (and, during the transition, the older action_id).
resolve(pill_key, retailer)
The one function every tap goes through. It returns a PillData or None. kind:uuid → the per-pill record, never the registry. Bare kind → the registry row. None → the label is sent as if the retailer typed it.
PillData
What a tap resolves to: kind, intent, prompt, label that was sent, preload, analytics. The rest of the pipeline sees only this type.
Binding
One stored PillData for one offered kind:uuid pill, written by the server when the pill is emitted. Today the map last_turn_pills on session state; next, a BE table (the bindings store). Retailer-scoped.
Miss
A kind:uuid tap with no binding (expired, replaced, or another retailer). resolve returns None; the label runs as typed text. It never falls back to the bare kind or to that kind’s fixed prompt.
Preload (pre-execution)
Work a pill declares to run before the model: entities and typed facts to put in context (ContextPreload), or a registered tool to run (ToolPreload, COM-1214). The field is named preload in code; its shape is open.

Who writes the ask

Catalog pill
A kind whose registry row has a fixed prompt and that the DAG is allowed to serve as an initial pill. The DAG chooses which products show it and writes the button label; RA’s row owns the prompt. All initial pills are catalog pills. A catalog kind can also be offered in chat (compare).
Preset follow-up
A follow-up with a fixed label and prompt on its row. The model only chooses to offer it. Key is the bare kind; nothing is stored per pill. Today: compare_similar_products.
Bound follow-up
A follow-up whose label and prompt the model writes for this turn, using a registered kind (mlt_add, catalog_explore, ask_<intent>). The server mints the uuid, builds the key kind:uuid, and stores the binding. The model never types a kind string; it picks from a schema built from the registry.
Staged follow-up open
Proposed: a tool writes the prompt from data it has (the anchor’s price), returns a staged id, and the model only places {staged_id, label}. See Scope.

03 How a tap works

Three cases cover every tap. Each shows how the pill is created and what happens when it is tapped, with the concrete values in the steps under each flow. Initial pills and follow-up pills take the same path through resolve().

@dataclass(frozen=True)
class PillSpec:          # one registry row
    kind: str
    intent: IntentType | None              # None = base assistant
    prompt: str | None = None              # fixed ask, for taps with no instance
    label: str | None = None               # fixed English copy, if this kind has one
    eligibility: Eligibility | None = None # catalog only, e.g. C3 list
    preload: tuple[PreloadSpec, ...] = ()

    kind: str
    intent: IntentType | None
    prompt: str | None
    label: str | None                      # the copy that was sent; never shown to the model
    preload: tuple[Preload, ...]           # ContextPreload | ToolPreload
    analytics: Mapping[str, str]           # logged only, never read to answer

04 Storage and migration

Only bound follow-ups store anything per pill. Initial pills and preset follow-ups resolve from the registry and have no storage question.

Order of change

  1. Table + actions land (BE). Nothing reads them. Table provisioned with TTL enabled.
  2. Encoder writes both. Each emitted bound pill is put in the table and in last_turn_pills.
  3. resolve() reads the table first, then last_turn_pills. A hit in either is the same PillData.
  4. Stop writing last_turn_pills once the frontend sends pill_key on every tap (Path §5). The map and PillBinding are deleted then.

No data migration. A binding is only useful for a pill that is still on someone’s screen, and today those live at most one turn. There is nothing worth copying from the old map into the table; the table is simply written from step 2 onward and the old map ages out on its own. There is no “v2” of the old storage in between.

Two read paths for a while, one write shape. Between steps 3 and 4, resolve() consults two stores. That is the only place the duality shows; callers see one PillData.

Wire transition

  • PillClickAction.pillKey is the permanent field. PillClickAction.actionId and MessageAction.pillKey are transitional and accepted until old clients are gone.
  • Until the frontend sends pillKey on every tap, last_turn_pills stays keyed by action_id; resolve() accepts either.
  • Status: BE proto field is in a draft PR; the frontend one-shape PR follows the proto and DS deploy. This is hub Path §4, then §5.

On TTL: the reason for a table at all is a retailer who comes back and taps a pill still on screen. Binding TTL is 1 day from write. Expired rows are misses. A TTL-bounded table does not grow without bound.

05 Ownership: DAG vs RA

Initial pills are produced by an Airflow DAG (compass_pdp_chat_prompt_pills) into a BE-served table; follow-up pills are produced by RA code at the end of a turn. They share no code on purpose.

DAG (initial pills)RA (registry, follow-ups, resolve)
DecidesWhich products show which initial pills, the button copy, slot order, eligibility gates. Copy tests mint a new key per wording.What a kind means: intent, prompt, preload. Which follow-ups the model may offer this turn.
Runs whereAirflow / Snowflake, daily, outside the RA app and its deploys.Inside the RA app, per request.
ContributorsAnyone shipping a pill experiment; SQL and a key.RA engineers; Python under core/.
ContractThe manifest: a checked-in list of catalog kinds (kind → intent, eligibility, fixed label if any). An RA test keeps it equal to the registry. An Airflow test fails if the DAG serves a key not in it, gates it differently, or serves a different label for a kind whose label is fixed.

Why DAG and RA do not share code. Consistency is already a test, not a shared import: an Airflow test fails if the DAG serves a key that is not in the RA registry, and an RA test keeps the manifest equal to the registry. Importing from the RA app is mechanically possible, but the DAG is wired to a different flare app (PdpOverviewAppV2Executor / pdpoverviewapp), which makes that import odd. They also have separate deploy timings, so an import would be misleading: a registry removal still cannot land before the DAG stops serving that kind, or taps miss. The DAG is a different repo surface with a different cadence and different contributors besides; importing the RA package would couple a daily SQL job to an app release and put product-copy experiments behind RA code review. The manifest is the contract without that coupling. BE stays a proxy: it serves the DAG’s rows and forwards taps; it does not interpret keys.

06 Decisions locked

  • One registry, REGISTRIES.pills, in RA Python. Kinds are cheap; intents are jobs. Many kinds → one intent, or none.
  • A pill carries only its prompt. How to answer lives in the intent’s playbook.
  • resolve(pill_key, retailer) → PillData | None; one path for initial and follow-up taps.
  • Intent is optional on a pill (ask, intent=None).
  • The tap prompt is the next user message. The label is never the user message on a hit.
  • Miss on kind:uuid → label as typed text; never strip to bare kind, never the kind’s fixed prompt.
  • One opaque pillKey string on the wire (hub contract), not separate kind and uuid fields; the warehouse derives pill_kind.
  • Follow-ups registered standalone as FollowUpPill, not as intent hooks. The model fills instance fields only; it cannot invent a kind.
  • Generic model-written pills use the reserved ask family; bare :uuid is not minted.
  • Amazon stays on product_research; no Amazon intent.
  • Labels live on both PillSpec (fixed English copy) and PillData (what was sent).
  • Bindings move to a retailer-scoped BE table with a 1-day TTL; the encoder writes them; resolve rejects a retailer mismatch.
  • Exactly three follow-up slots. Manifest + Airflow test for DAG keys.

— Still open

These are initial ideas, open to other suggestions. Scope lists the product-level opens (staged pills, preload shape). The rest:

  1. Manifest test scope. Category pills first, or every catalog kind?
  2. Pinning. A pinned pill takes one of the three slots; a fourth would change the schema and the frontend layout.
  3. Emission log. One server event per emitted pill ({pill_key, kind, label, analytics}); CTR by kind does not exist without it.
  4. Custom fields on a follow-up. A FollowUpPill may supply its own pydantic model when a pill needs structured input. Nothing needs it today.

Later: server-side compare availability

Compare should only show when there are products to compare. Today the frontend checks (isCompareAvailable, COM-843). Moving that into compare’s check needs a cheap candidate check at the end of each turn (which can double as compare’s preload), measurement of pick rate before and after, then removal of the frontend check. Compare keeps its bare key on the PDP and in chat.
