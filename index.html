Compass · Retailer Assistant · Path §3

Registry, resolver, and follow-ups

Replaces the post-#69192 stub (kind → IntentType(kind)). Hub: RA Pill Identity Infra §3 · routing: RA Intent Routing Infra.

v17 · plan · glossary drafted for Cedo · staged/authored proposed, not locked · open items at the bottom

The plan in short.
  • One registry of pill kinds (REGISTRIES.pills, Python code in RA). A kind can show up as an entry chip, a follow-up, a staged chip, or more than one of those.
  • A kind is cheap; an intent is a job. Many kinds can point at one intent, or at none.
  • A pill carries only its ask (prompt). How to answer lives in the intent’s playbook.
  • Every tap resolves to one PillData: intent (optional), prompt, preloads, and the label that was sent.
  • Follow-up pills are generic. Each is registered on its own, like a tool. The model writes every follow-up the same way: a kind, a label, a prompt, and entities.
  • RA logs each emission as {pill_key, kind, label, analytics}. Today only the frontend records impressions and clicks.

G Glossary + one-tap walkthrough

Drafted for Cedo. Terms for reading the rest of this plan. Staged vs authored is proposed, not locked — it does not change the v17 decisions, kinds table, or open questions below.

There is no Chip class and no Mode field in the landed types. In code, _staged is only the in-turn bound-chip buffer.

Glossary

  • Chip — the button on the wire (label + action_id + pill_key).
  • Pill — the registered identity behind that button (kind, optional intent, the ask).
  • Kind — frozen lower_snake name in REGISTRIES.pills (sold_on_amazon, mlt_add, ask). Many kinds can share one intent, or none. Not an IntentType (product_research is not a pill key).
  • Mode (no field) — who wrote this instance: catalog/entry (DAG, bare kind); follow-up authored (model, kind:uuid); preset follow-up (fixed label, still bare kind). Compare is catalog and follow-up on one PillSpec.
  • Catalog / entry pill — PDP strip chip from the DAG bank. DAG owns the copy (label); RA owns the tap ask (prompt). Not the follow-up kind catalog_explore.
  • Follow-up pill — FollowUpPill row in REGISTRIES.follow_ups: a kind the model may offer after a turn. Same PillSpec table; compare is one object in both.
  • Preset — fixed spec.label; encoder emits bare kind, writes no binding (compare_similar_products).
  • Bound — emit_follow_up mints a uuid; chip carries kind:uuid; finish writes last_turn_pills[uuid].
  • Staged (proposed, not locked) — so dimension chips like mlt_cheaper and mlt_ships_faster keep correct values from retrieve (e.g. $18.40, not “under $20”). Tool writes the ask via stage_pill(...) → id; model only places {staged_id, label}. Not landed. Shipped path is authored emit_follow_up / bound kind:uuid. Optional later collapse: one staged mlt_add with facts.dimension. In code, _staged is only the in-turn bound-chip buffer.
  • **pill_key** — kind (catalog or preset); kind:uuid (bound; uuid = action_id); ask:<uuid> / ask_<intent>:<uuid>. Leading : is rejected.
  • Ask — (1) reserved kind ask (intent=None); (2) ask_<intent> generic intent chip; (3) the prompt, the next user message. On a resolve hit, the chip label is never that message.
  • Generic — (1) ask / ask_<intent> freeform chip; (2) a kind's fixed PillSpec.prompt on a bare-kind tap; (3) resolve → None → typed text (chip label). A kind:uuid miss must not use (2).
  • **PillSpec** — registry row (kind, intent, optional fixed prompt/label).
  • **PillData** — what resolve() returns for this tap.
  • **FollowUpPill** — a spec plus docs, optional check / pydantic model+encode.
  • Binding — last_turn_pills[action_id]: intent, prompt, tokens, pill_key. Replaced every finish. 3-day Dynamo (PR-D) not read by resolve yet.
  • Resolve — tap (action_id and/or pill_key) → PillData | None. Uuid/action_id → bindings only (never the registry). Bare kind → registry. None → typed text.

Why a 3-day bindings store?

last_turn_pills is wholesale-replaced every finish. A back-button, reopened panel, or other-tab tap on an earlier chip already misses and becomes the label as typed text (case C). The 3-day retailer-scoped Dynamo store exists so those later taps still hit the same stored prompt and intent. A miss still never strips to bare kind and never runs that kind’s generic registry prompt. TTL only starts to matter once DS reads that store.

01 Why

Pills are how most retailers start and continue an RA conversation. Today a tap is handled three different ways: entry pills run as typed text (their key only picks a guidance string), compare-similar is an intent the frontend sends, and generated follow-ups look up a map that lasts one turn. Most behavior lives in prompts. A registry fixes four things:

  • Consistency. A kind behaves the same on every tap, as an entry chip or a follow-up, because code sets its intent and prompt. Prompting alone makes behavior hard to guarantee or customize; More Like This entry is “less solidified in code” without it.
  • Latency. The core principle is to do work on this turn so the pill answers fast on the next. A pill that carries its preload (e.g. “Sold on Amazon” carrying its search, latency opportunity, COM-1214) skips an LLM round trip.
  • Control of follow-ups. Today a follow-up appears only if the model writes it. With server-defined kinds an intent can offer, hide, or pin chips — e.g. the MLT PRD’s always-first “show me more” plus random dimension chips.
  • Testing and analytics. A stable kind is the unit we read CTR on. Catalog copy tests today mint a new key per wording; that stays the DAG’s job. Fixed-copy kinds (compare) keep one kind and one English label on the spec. The pills experiment roadmap (§5) lists pills that need this: a “margin at this price” follow-up, “compare with the one you just viewed”, “what else gets me to this brand’s minimum?”, and faster More Like This.

The current stub only works when the kind string equals an IntentType. It can’t point several kinds at one intent, carry a prompt or preload, or see follow-up kinds.

02 The registry

REGISTRIES.pills is a Python registry in RA, like REGISTRIES.tools. It is not a Dynamo table. Dynamo holds two other things: the DAG’s serving rows (flare-host.compass_pdp_chat_initial_pills: product → [{key, label, group, context}]) and, later, the bindings store (§03). A duplicate kind fails at import.

Who owns what. The registry owns what a kind means (intent, optional fixed prompt, optional fixed English label, preload, eligibility). The DAG owns which products get which catalog chip and that chip’s copy; wording tests there mint a new key. flare-host also serves some entry chips (today, compare) from the same registry, and it pins, shuffles, caps and cohort-gates the PDP list. The DAG doesn’t import RA code: RA checks in a manifest (a test keeps it equal to the registry). An Airflow test fails if the DAG serves a key missing from it, gates it differently, or serves a different label for a kind whose PillSpec.label is set. The manifest does not push catalog copy into the DAG.

Mode is per chip, not per kind. It names who wrote this instance’s prompt and entities, and when. That decides whether the tap needs a binding. A kind can have more than one mode — compare is an entry chip from flare-host and a follow-up in chat, both using the same spec.

03 Resolving a tap

@dataclass(frozen=True)
class PillSpec:          # one registry row
    kind: str

    prompt: str | None = None              # fixed ask, for taps with no instance

    eligibility: Eligibility | None = None # catalog only, e.g. C3 list

@dataclass(frozen=True)
class PillData:          # what a tap resolves to
    kind: str
    intent: IntentType | None
    prompt: str | None
    label: str | None                      # the copy that was sent; never shown to the model
    preload: tuple[Preload, ...]           # ContextPreload | ToolPreload
    analytics: Mapping[str, str]           # logged only, never read to answer

def resolve(pill_key, retailer) -> PillData | None

Two places a tap can resolve:

  • The registry holds one row per kind: what that kind of chip means. Engineers write it in code.
  • The bindings store (Dynamo) holds one PillData per chip (kind:uuid): the prompt, entities and label of one specific chip. The encoder writes it when the chip is created. It has a 3-day TTL and rejects a tap from a different retailer. Until it ships, last_turn_pills is the stand-in — but each turn replaces that map, so a tap on an older chip or from another tab misses today. The 3-day store will start resolving those; that is intended.

A kind tap builds PillData from its row plus the page (label from the spec if set, else the text the frontend sent). A kind:uuid tap reads it from the store. Either way the rest of the pipeline sees one type.

Where the label lives

  • PillSpec.label is the English source of truth for kinds with fixed copy (compare, “Show me more”). The frontend localizes by kind. It replaces today’s three copies of the compare string (RA preset, flare-host constant, frontend).
  • PillData.label is what was actually sent. Bindings store it for kind:uuid chips. A tap built from a bare kind uses the spec’s label, or None.
  • Catalog copy stays on the DAG row. The registry does not own it, and copy tests there keep minting new keys.
  • The tap still sends the label as the user message. Nothing resolves through that text. The stored label is for logging, and to flag a mismatch with what the client sent.

Emission log. RA has no server impression event today; only the frontend’s impression and click events carry the label. Each emitted chip gets one server event {pill_key, kind, label, analytics}. That is what makes CTR by kind joinable. Model-written chips today go out with action_id rather than pill_key, so their CTR can only be read by label text until the key switch lands.

Intent and prompt

  • intent picks the job. None is allowed: the turn runs like a typed turn (base prompt, base tools, switch_intent available).
  • prompt is the pill’s ask, the only text it sends beyond its label. It replaces the hub’s guidance and PillBinding.prompt.
  • Rule: anything like “when answering X, do Y” belongs in a playbook, so that pill needs an intent. This keeps _GUIDANCE_BY_PILL_KEY from coming back.

Preload

  • ContextPreload(entities, facts): loaded into the turn, nothing runs. entities are tokens to fetch (products, brands; “compare these three”). facts are typed data RA can’t work out at tap time (why the DAG showed the chip, a filter to apply). Typed, so they never become a second prompt.
  • ToolPreload(tool_name, arguments): a registered tool run before the model, entering as if the model had called it (COM-1214).

Rows hold templates (“retrieve with the page product”); stored chips hold the filled-in values. The retailer comes from the session, never from the pill.

04 Follow-up pills

A follow-up pill is registered on its own, next to its intent’s code, the way tools register. Intents don’t declare follow-ups. The schema builder, cleanup passes and encoder in core/follow_up_pills.py stay; they read these registrations instead of intent hooks.

@dataclass(frozen=True)
class FollowUpPill:
    spec: PillSpec                 # kind, intent, prompt, label, preload
    docs: str                      # when the model should use it
    check: Callable[[TurnRunContext, Chip], PillData | None] | None = None
    max_per_response: int | None = None

@dataclass(frozen=True)
class Chip:                        # what the model writes, for every follow-up
    kind: str                      # one of the registered follow-up kinds
    label: str | None = None       # ignored when the spec has a fixed label
    prompt: str | None = None      # ignored when the spec has a fixed prompt
    entity_tokens: tuple[str, ...] = ()

REGISTRIES.add_follow_up(FollowUpPill(...))
  • Same inputs as every pill. A follow-up resolves to the same PillData as an entry pill: prompt and preload, with entities in ContextPreload.entities, plus the label that was sent.
  • Fixed or model-written. A spec with a fixed label and prompt (compare) is one the model only chooses. A spec without them (add, relax, explore; catalog explore; ask_<intent>) is one the model writes.
  • check is optional. It sees the turn and the chip, can drop it (no grid this turn, an ask the search can’t serve), and can add server data (the anchor product). Without it, the chip’s prompt and entities go straight into PillData.
  • Gating follows the pill’s intent: a gated-off intent’s pills are left out, as today. An active intent can still hide others’ pills with suppressed_follow_ups() (today’s suppressed_preset_pill_ids()).

What the model sees

One chip shape. Its kind field lists every follow-up kind with its docs. The schema is built once per gate state, as today. Staged chips use a small extra shape, {staged_id, label}.

Staged chips

A tool stages a chip with run_context.stage_pill(kind, prompt, preload, label=None, pin=False) and gets back an id, which it returns in its result so the model can place it. If label is omitted, the spec’s fixed label is used when it has one. A pinned chip is placed first and takes one of the three slots (the model’s last chip is dropped). Unknown staged_ids, including ones copied from an older turn, are dropped. The model cannot write a staged kind as a plain Chip; that is dropped too. Only tools that stage chips touch this. Compare’s pills-only custom-response run must share this turn’s run context so staged chips from tools in that run can be placed.

What the encoder does each turn

  1. Validate the block. If it’s invalid, show no chips (as today).
  2. Put pinned staged chips first; swap each staged id for its chip; drop unknown ids.
  3. Run each pill’s check; drop chips it rejects and hidden kinds.
  4. Per-pill limits and label dedupe, as today.
  5. Keep exactly three, as today. Don’t refill dropped slots; count drops in a metric.
  6. Create the key. For kind:uuid, write PillData (including the sent label) to bindings. Emit {pill_key, kind, label, analytics} and send the chip. Unplaced staged chips are never written.

Add vs dimension chips

These look the same in the product — both add one constraint to the current search — but they are different kinds because a different writer owns the ask.

  • Add / relax / explore are model-written. The model invents the constraint from the conversation (“only ceramic”, drop “under $20”, try a nearby style), writes the label and prompt, and check drops asks the search can’t do. Relax is only valid for a term that’s already applied. Explore is an adjacent ask, not a filter on this grid.
  • Dimension chips are a closed PRD list (cheaper, ships_faster, no_minimum, made_in_country, ships_from_country). The retrieve tool sees which of those are still eligible, draws one or two at random, and writes the exact ask (e.g. “Show me more like this under $14 wholesale” from the anchor’s wholesale price). Staging exists so the model cannot paraphrase that number away.

Keeping them as separate kinds also keeps CTR per dimension without parsing labels. Collapsing dimensions onto mlt_add (staged, with facts.dimension) is possible later if we want fewer rows.

The same split applies outside MLT: a follow-up the model should invent is a FollowUpPill the model writes; a follow-up whose ask is already computed this turn is staged.

05 A tap, end to end

flowchart LR
  tap["tap pill_key"] --> resolve["resolve()"]
  resolve --> none["None → typed text"]
  resolve --> data["PillData"]
  data --> gate{"gated / can't start here?"}
  gate -->|yes| refuse["refuse, keep state"]
  gate -->|no| run["intent playbook, or base if None"]
  data --> pre["load context, run tool preloads"]
  run --> fu["encoder → chips"]
  1. The frontend sends back pill_key (and, during the switch, still action_id); resolve returns PillData or None (typed text).
  2. If the intent is gated or says it can’t start on this page, refuse and keep state. The page check moves into the intent; core’s hard-coded “needs a product page” goes away.
  3. Activate the intent (or none), load ContextPreload, run ToolPreloads, and send the prompt (where it goes is an open question below).
  4. Answer, then build follow-ups through the encoder.

Entry and follow-up taps take the same path.

06 Intents are jobs, kinds are cheap

A new intent is little code (an IntentType, a folder with summary, playbook and activate, one registration). The cost is elsewhere: its summary is in every turn’s prompt, it’s one more option for routing to pick wrongly, it must start from just the page and text, and it needs a playbook, gate and evals. So a new pill is a new kind on an existing intent. A new intent is for when a job outgrows its playbook.

  5. Pinning. A pinned chip takes one of the three slots; a fourth chip would change the schema and the frontend layout.
  6. Key switch. Follow-ups today send action_id, and pill_click.action_id is required. Moving to kind:uuid on pill_key needs a frontend and proto change. Accept both until old clients are gone. Fine that this takes time.
  7. Emission log. New server event per chip. Fine that this is new work; CTR by kind does not exist without it.
  8. Amazon preload. Ship with the fixed prompt only, or add ToolPreload(web_search) too?

Later: server-side compare availability

Compare should only show when there are products to compare. Today the frontend checks (isCompareAvailable, COM-843). Moving that into compare’s check needs:

  • A cheap candidate check at the end of each turn. If it fetches candidates, it can also be compare’s preload.
  • Measurement: how often compare is picked before and after, plus drop counts.
  • Then remove the frontend check.

Compare keeps its bare key (compare_similar_products) on both the PDP and in chat, because its label and prompt are fixed on the spec.
